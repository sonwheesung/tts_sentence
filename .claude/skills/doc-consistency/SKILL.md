# doc-consistency — 문서 정합 검사 (범용 골격)

> **왜**: 타입 검사도 테스트도 문서를 읽지 않는다. 그래서 **문서는 조용히 틀린다.**
> 다음 세션이 그 문서를 정본으로 믿고 판단하므로, 문서 드리프트는 코드 버그보다 오래 산다.
>
> **경계**: 코드가 명세대로 *도는가*는 테스트 · 런타임 검증이 본다. 이 스킬은 *문서 자체가 진실과 맞나*를 본다.
>
> 이 판은 **2026-09-18** 에 형제 레포 셋의 판을 합쳤다(아래 §9 계보). 그 전 판은 2026-08-26 에 멈춰 있었고,
> 그사이 형제 판들이 축 둘과 운영 규칙 여럿을 더 얻었다. **범용본이 항상 최신인 것은 아니다.**

---

## 0. 🔴 반드시 지킬 것

1. **정본을 먼저 정한다.** 두 서술이 다르면 어느 쪽이 진실인가부터. 기본 순서:
   **코드 · 실측 > 결정 기록(CLAUDE.md 결정 절 등) > 시스템별 상세 문서 > 요약(README · 현황표 · 진행표)**.
   요약이 상세와 다르면 **거의 항상 요약이 낡은 것**이다.
2. **일괄 치환 금지.** 문서에는 계획("이래야 한다")과 실측 기록("저쪽은 이랬다")이 섞여 있다.
   일괄 치환이 콘솔 실측 기록을 덮어쓴 전례가 있다(delvewarden 2026-08-21). **한 건씩, 그 줄이 계획인지 기록인지 보고** 고친다.
3. **지우지 말고 정정한다.** 뒤집힌 결정은 취소선 + 날짜 + 이유로 남긴다. 지우면 다음 세션이 같은 질문을 다시 한다.
   날짜가 박힌 스냅숏(테스트 리포트 · 옛 CHANGELOG 항목)은 그때의 사실이라 고치지 않는다.
4. **문서를 코드에 맞출지, 코드를 문서에 맞출지는 사람이 정한다.** 설계만 하고 아직 안 만든 것은 결함이 아니라 계획이다. 마킹만 한다.
5. **코드 결함을 찾으면 고치지 말고 적는다.** 문서 감사가 코드를 고치기 시작하면 범위가 터진다. 별도 작업으로 넘긴다.
6. **프로젝트 규칙이 문서 수정을 막는 자리를 확인한다.** 예: My Word 는 `CLAUDE.md` 를 고치기 전에 사용자에게 올린다.
   그런 문서는 찾아서 **보고까지만** 한다.
7. **못 고친 것은 보고에 남긴다.** 조용히 넘기면 다음 감사가 같은 것을 또 찾는다.

## 1. 먼저 기계, 그다음 사람

**셀 수 있는 것은 가드로 만든다.** 사람은 문장을 본다. 가드가 이미 본 개수를 사람이 다시 세지 않는다.

| 형제 레포의 가드 | 무엇을 세나 |
|---|---|
| diary `check:doc-counts` · `scan:doc-refs` · `scan:doc-symbols` | 문서가 적은 개수 · 파일 참조 · 코드 심볼 |
| dungeon_guide `check:docs` | 문서 링크 · 세는 법이 적힌 수 |
| my_word `check:docs` | 화면 · 서비스 · 컴포넌트 · 저장 키 **이름 집합**(양방향 차집합) |

🔴 **가드 규칙 셋** (전부 실제로 데였다):
- **개수가 아니라 이름 집합을 비교한다.** 하나 빠지고 하나 늘면 개수는 같다.
- **이름은 경계로 찾는다.** 부분 문자열로 찾으면 `@my_word_srs` 가 `@my_word_srs_old` 안에서 찾아져 초록이 된다(my_word 2026-09-18).
- **새 가드는 일부러 망가뜨려 빨개지는 것까지 본다.** 통과만 본 가드는 허위 오라클이다.
  위 구멍도 회귀 주입에서 나왔다. diary 의 시간대 가드는 **단언을 전부 지워도 초록**이었다.

⚠ 가드가 초록이면 **가드가 세는 것만** 맞다. 이름이 문서에 있어도 그 설명은 반년 낡았을 수 있다(§2 축 ⑦).

## 2. 일곱 축

### ① 상호참조 무결성
문서 링크 · §절 인용 · `파일:줄` · 코드 식별자 인용이 실재하나.
- 절 번호 인용(`AUTH §7.5`)은 문서를 개편하면 조용히 어긋난다. **별칭 표기부터 통일하면 검사가 싸진다.**
- 🔴 **"MISSING" 인데 파일이 다른 경로에 실재하는 것**을 넘기지 않는다(`lib/x.ts` 가 실제로는 `server/lib/x.ts`).
  경로가 그럴듯해서 넘기기 쉽고, 다음 사람이 거기서 찾다가 없다고 판단한다.

### ② 문서끼리 모순 (한 사실에 두 값)
프로젝트마다 **교차축 표**(두 곳 이상에 적히는 사실 · 정본 · 함께 적히는 곳)를 만든다. 흔한 축:
버전 · 개수(화면 · 테스트 · 에셋) · 구현 현황(✅ · ❌) · 저장 키와 백업 범위 · 정책 상수 · 서버 주소 · 명령어.
> 실증: delvewarden 에셋 개수가 한 파일 안에서 `58/67`, 다른 절 `67/67`, README `69/69` 였다. 요약 셋이 각각 다른 시점에 멈춰 있었다.

### ③ 문서↔코드 존재 정합
문서가 적은 시스템 · 파일 · 상수 · 스크립트 · 키가 실재하나. 반대로 **코드의 큰 것이 문서에 홈이 있나.**
- 새 가드 스크립트가 README 검증 절에 없으면 아무도 안 돌린다. **도구를 만들면 그 도구를 가리키는 문서까지가 일이다.**

### ④ 폐기된 결정 정리
뒤집힌 결정의 옛 서술이 다른 문서에 **현역 지시문**으로 남았나. 프로젝트마다 "되살아나면 안 되는 것" 목록을 grep 한다.
- 🔴 이 grep 은 오탐이 많다. 폐기의 **근거**를 설명하는 줄도 걸린다. 남길 것은 *"그렇게 하라"* 고 말하는 줄뿐이다. 문장의 서법을 보고 판정한다.

### ⑤ 검증 주장 과장: 맞는 사실을 실제보다 넓게
"✅ 3개 언어 확인" 이면 다음 사람은 그 세 언어를 **다시 안 본다.** 틀린 값은 언젠가 부딪혀 드러나지만 넓은 ✅ 는 안 드러난다.
- 검사: ✅ 를 볼 때마다 *"이 문장이 주장하는 범위를 전부 실제로 봤나, 계산했나?"* 특히 전칭 · 복수형("모두 · 전 화면 · N개 언어").
- 교정: 지우지 말고 **근거 수준을 낮춘다.** `✅ 3개 언어 확인` → `✅ pt 실기기 · ⚠ en · ja 는 계산상`. 사람 평결이 필요 없다.
- 🔴 **0 이 나오면 대상이 아니라 세는 방법을 의심한다.** 대조군을 먼저 센다.
  (diary: Hermes 는 비ASCII 를 UTF-16LE 로 넣어 번역 0건처럼 보였다 · my_word: `aapt2` 검색식이 틀려 알림 아이콘 0줄)
- 🔴 **닫는 것도 주장이다.** 근거를 못 찾으면 ⑥ 에서 닫지 않고 열어 둔다.

### ⑥ 끝난 일이 남은 일로 남았나 (⑤ 의 반대 방향)
끝난 일이 🔴 · `- [ ]` · ❌ · ⏸ · "대기" · "미정" 으로 남아 **없는 블로커가 크리티컬 패스에 오른다.** 실제로 일정을 늦춘다.
diary 일곱 번, delvewarden 네 번, my_word 셋(2026-09-18).
```bash
grep -rn "^\s*- \[ \]" docs/*.md CLAUDE.md
grep -rn "🔴\|❌\|⏸\|🔄" docs/README.md CLAUDE.md | grep -v "~~"
grep -rn "미구현\|미착수\|진행 중\|대기\|예정\|미정\|아직\|검증이 남았다" docs/*.md CLAUDE.md | grep -v "~~"
```
- ★ 공통 원인: **"끝났다고 적는 일"이 작업의 마지막 칸**이라 빠진다. 또는 한 줄은 고치고 **같은 사실을 말하는 옆 줄**을 안 고친다.
  → 끝났다고 적을 때 grep 으로 그 사실을 말하는 다른 줄을 찾아 함께 닫는다.
- ⚠ ⏸ 는 "못 한 것"과 "안 하기로 한 것" 둘 다에 쓰인다. 후자는 그대로 둔다.
- ⚠ **버전 번호가 있는 절 = 나간 릴리스가 아니다.** my_word 1.5.0 절은 길게 있지만 스토어에 따로 나가지 않고 1.6.0 에 합쳐졌다.
  감사하던 사람도 처음에 "1.5.0 으로 나갔다"고 적었다.

### ⑦ 목록 문서 드리프트: 기능은 늘었는데 목록 문서가 안 따라왔다 (2026-09-18 my_word 에서 얻음)
화면 목록 · 서비스 목록 · 저장 키 표 · 컴포넌트 트리처럼 **코드를 열거하는 문서**가 기능 추가를 못 따라온다.
기능마다 결정 문서에는 긴 절이 생기는데 구조 문서는 몇 달 전에 멈춘다.

| my_word 2026-09-18 | 문서 | 실제 |
|---|---|---|
| 화면 목록 | 9개 | 15개 |
| 저장 키 | 4개 | 14개 + SecureStore 2개 |
| 서비스 | 4개 | 13개 + SDK 폴더 |
| README | 화면 13개 · 테스트 199개 · 런타임 버전 1.3.3 | 15개 · 288개 · 1.6.0 |

🔴 **개수 드리프트는 내용 드리프트의 겉면이다.** 목록에 있던 화면도 설명이 틀려 있었다(주관식만 적힌 퀴즈에 객관식 · 복습 모드가 있었다).
→ 개수를 맞추고 끝내지 않는다. 빠진 것을 채울 때 **옆 항목의 설명도 코드에서 다시 뽑는다.**

**검사법**: 코드에서 이름 집합을 뽑고(`ls src/screens` · 저장 키 리터럴 grep) 문서의 집합과 양방향 차집합. 가드로 만든다(§1).
**쓰는 쪽 규칙**: 새 화면 · 서비스 · 키를 만든 커밋에 문서 한 줄을 같이 넣는다. README 에 개수를 손으로 적지 않는다(적으면 가드가 재게 한다).

🟢 **부수 효과**: 설명을 코드에서 다시 뽑는 일이 곧 코드 리뷰가 된다. my_word 는 이 작업에서
"복습 배너에서 시작한 퀴즈의 `다시 풀기`가 홈으로 떨어진다"는 운영 중 결함을 찾았다(§0 규칙 5 대로 별도 작업으로 넘겼다).
사실을 뽑을 때 **"문서에 옮기면 틀리는 동작"을 따로 모아 달라**고 하면 이런 것이 모인다.

## 3. 문서만 보지 않는다

- **메모리**(`~/.claude/projects/<프로젝트>/memory/`): 낡은 메모는 컴팩트마다 다시 들어와 문서보다 먼저 판단에 들어간다.
- **인계 문서**(`worklist-<날짜>.md`): ⑥ 이 가장 잘 나는 곳이다. "대기 중" 표를 실측으로 닫는다.
- **게시 중인 문서**(법무 `.html` · 스토어 등록정보): 어떤 가드도 안 본다. 게시 브랜치가 개발 브랜치보다 뒤처지면 공개본이 조용히 낡는다(diary 2026-08-27, 4일 · 66커밋).
- **살아 있는 상태는 문서가 아니라 그것에게 묻는다**: 서버 health · 스토어 페이지 · 콘솔 상태 문구.

## 4. 기지(旣知) 오탐 기준선

🔴 **"깨짐 0" 이 목표가 아니다.** 문서는 레포 밖 공용 문서와 형제 프로젝트를 정본으로 가리키므로 단순 스캐너는 정당한 인용을 깨진 것으로 센다.
**개수가 아니라 유형으로 판정한다.** 흔한 정상 유형:

| 유형 | 예 |
|---|---|
| 레포 밖 공용 정본 | `C:\project\common\*.md` |
| 형제 프로젝트 인용 | `common_server/...` · 다른 앱의 docs |
| 상대경로(스캐너 한계) | `../CLAUDE.md` |
| 문서가 **부재를 명시**한 것 | "❌ 미작성" · "만들지 않았다" · "쓰지 않는다" (이게 정상 신호다) |
| 빌드 · 런타임 산출물 | `android/*` · `mapping.txt` · 복원 중 센티넬 |
| 레포 밖 비밀 | `credentials/*` · `*.jks` |
| 이전 이력 인용 | `A → B` 의 왼쪽 |

프로젝트판에 **날짜 박힌 기준선 표**를 두고, 감사 때마다 **늘어난 것만** 본다. 새로 깨진 것은 이 목록에 넣지 말고 고친다.

## 5. 절차

1. **범위**: 전체, 또는 변경이 닿은 문서 군과 이웃
2. **기계**: 프로젝트 가드를 돌린다(§1). 빨간 채로 읽은 문서로 판단하지 않는다
3. **사람**: 축 ①~⑦. 문서가 많으면 병렬로 나눈다. 코드에서 사실을 다시 뽑는 일은 하위 에이전트에 맡기고, **문서 쓰기는 한 사람이 한다**(문체 · 정본 판정을 한 곳에서)
4. **평결 + 교정**: 정본이 갈리는 것만 사람에게 올린다. 나머지는 문서를 실측에 맞춰 한 건씩 고친다
5. **기준선 갱신**: 오탐 표 · 가드 바닥값 · 교차축 표

## 6. 산출물

```
## 문서 감사: <범위> (<날짜>)
### 정본이 갈린 것 (사람 평결)        | 무엇 | A | B | 정본 후보 | 근거 |
### 고친 것                            | 문서 | 무엇이 틀렸나 | 무엇으로 | 정본 |
### 수정이 막힌 문서에서 찾은 것 (보고만)
### 과장된 ✅ (근거 수준을 낮춘 것)
### 끝난 일로 닫은 것 · 근거가 없어 열어 둔 것
### 코드 쪽 결함 (별도 작업)
### 오탐 (다음 감사가 또 찾지 않게)
### 못 고친 것 + 왜
```
🔴 **오탐 절을 반드시 쓴다.** 안 쓰면 다음 감사가 같은 것을 또 잡고 또 아무것도 아니라는 결론에 도달한다.

## 7. 프로젝트판 만드는 법

그 레포 `.claude/skills/doc-consistency/SKILL.md` 에 **이 골격을 베끼지 말고** 그 레포의 것만 적는다:
문서 지도와 정본 순서 · 수정이 막힌 문서 · 교차축 표 · 검사 명령 · 가드 이름 · 기지 오탐 기준선(날짜) · 그 레포의 **지배적 결함**(실제 사례 표).

🚫 **한 레포에 문서 감사 스킬을 둘 두지 않는다.** 트리거가 겹쳐 어느 쪽이 불릴지가 운이 된다.
dungeon_guide 는 이름을 `doc-audit` 로 하고 이 골격을 흡수했다. 그 레포에 `doc-consistency` 를 따로 복사하지 않는다.
